# Disposable migration reconciliation rehearsal (proposal only)

This document is a review plan, not an executable script. It must not be copied into a production or staging shell. No database is provisioned by this proposal.

## Preconditions and approvals

1. Obtain written approval naming a disposable host, database, owner, retention period and reviewer. The database must be a new throwaway schema isolated from `bluemarketing_l13_staging`, `bluenew`, production, and all financial systems.
2. Record the exact repository commit, migration-file SHA-256 manifest, server version, SQL mode, character set/collation, and Laravel/PHP versions.
3. Restore only an approved non-production snapshot containing synthetic or sanitized data. Do not use a live customer or financial export unless separately approved and redacted.
4. Use a temporary least-privilege account. Verify `DATABASE()`, `CURRENT_USER()`, `USER()`, `@@hostname`, `@@port`, grants, and the disposable database name before any migration command. Abort on any mismatch or write scope beyond the throwaway schema.

5. Use a unique name such as `blue_l13_rehearsal_20261028_<random>` generated by the administrator at execution time. The name must not equal `bluenew`, `bluemarketing_l13_staging`, any production schema, or any configured application database. Record the generated name in the approval record; do not hard-code it in application configuration.
6. Start from a clean process with `--no-defaults`, explicit TCP host/port, explicit disposable database, and an explicitly supplied temporary account. Clear inherited `DB_*`, `DATABASE_URL`, `MYSQL_*`, Laravel config-cache and saved-login environment variables before the client starts. Never source `.env` or bootstrap Laravel for the rehearsal.
7. The administrator must create the disposable database/account and later dispose of them in a separately approved change window. This proposal contains no CREATE USER, GRANT, CREATE DATABASE, DROP DATABASE, import, migration, or rollback command.

## Evidence and execution gates

- Capture a schema/history baseline before any operation, including tables, columns, indexes, foreign keys, checks, row counts and migration rows; store only approved metadata and aggregate counts.
- Verify backup checksum, restore completion, and a second independent metadata capture before rehearsal.
- Run no command until the baseline, identity gate, account grants, and exact file hashes are reviewed. Never replay the 35 CREATE candidates against a schema containing their tables.
- Test only an explicitly approved forward-only remediation or history-only simulation on the throwaway database. History-only simulation must not run `up()` or `down()` and must not insert application records.
- Capture exit codes, errors, lock duration, schema diff, migration-history diff, and aggregate row-count diff. A failed gate, unexpected object, changed count, or incomplete output is `BLOCKED`, not a successful rehearsal.

## Non-executable rehearsal sequence

The administrator must execute these phases manually, stopping after every failed gate. Each phase produces a sanitized, reviewable artifact before the next phase begins.

1. **Environment and identity:** verify the unique database name, explicit host, port, server version, `DATABASE()`, `CURRENT_USER()`, `USER()`, `@@hostname`, `@@port`, and `SHOW GRANTS`. Require a temporary account with access only to the throwaway schema. Any inherited target, unexpected grant, or account mismatch is `STOP`.
2. **Synthetic baseline:** restore only a sanitized/synthetic fixture, then capture table/column/index/FK/check metadata, migration rows, checksums and aggregate counts. Verify backup checksum and independently verify restore checksum. Do not read or emit business rows.
3. **Hash gate:** recompute all 38 migration hashes against the approved manifest and record the exact repository commit. A mismatch is `FAIL` and blocks all later phases.
4. **Cumulative dependency gate:** compare the full migration order and dependencies. Confirm existing-table collision targets, stock FK ordering, permission pivots, journal-voucher uniqueness drift, JSON/LONGTEXT differences, and the separate `expences`/`accounting_expenses` schemas. Do not infer migration execution from object presence.
5. **19 history-only candidates:** inspect each candidate's physical match and dependency evidence. Do not run `up()` or `down()`. A history-only simulation may use a copy of the migration ledger in an isolated rehearsal artifact only after approval; it must not modify application tables or the real `migrations` table. Require unchanged schema and aggregate checksums.
6. **13 forward-remediation candidates:** design and review each additive change separately. Rehearse only approved changes on a fresh disposable clone after data-validation, lock-impact, constraint and recovery review. Never use the original CREATE migration to repair a collision.
7. **Three UNKNOWN provenance targets:** keep `ledgers`, `sites`, and `booking_vouchers` blocked. Rehearse no disposition until each extra column/index/FK has independently established DDL provenance or an approved forward design.
8. **Three missing ALTER migrations:** treat `site_id`, `plots.amount`, and landing-builder fields as separate forward candidates. No historical backfill, attribution, or automatic history insertion is permitted.
9. **Post-run and recovery:** capture metadata, history, checksums and sanitized aggregates again. Compare against baseline. Any unexpected write, row-count change, schema drift, lock failure, cross-database access, or incomplete output is `RESTORE`, followed by baseline restore and independent verification.

## Laravel bootstrap safeguards (future approval only)

`--no-defaults` controls MySQL client option files; it does not isolate Laravel, PHP environment variables, cached configuration, service providers, or arbitrary application code. If a Laravel process is ever approved for the disposable rehearsal, use a separately copied, hash-pinned worktree. Do not run migrations from this project worktree.

Before bootstrap, the administrator must create a clean process environment containing only an explicit testing/rehearsal profile, disposable `DB_CONNECTION=mysql`, the approved throwaway host/port/database, and a temporary account supplied through a masked secret mechanism. Remove `APP_KEY`/credential values unrelated to the fixture, unset `DATABASE_URL` and all production/staging variables, and verify no `bootstrap/cache/config.php` or equivalent cache is present in the copied worktree. The copied application must fail closed if the database name, host, port, authenticated account, grants, or environment profile differs from the approved values.

The first application operation must be a pre-migration identity/grants probe that exits before Laravel's migration runner if any value is wrong. The process must then run only an explicitly reviewed migration allowlist against the disposable database, with network/firewall isolation preventing routes to staging, `bluenew`, master-live infrastructure, or production. Capture the exact command, environment allowlist, worktree hash, identity result, and migration SQL plan before execution. These safeguards require host/process tooling and cannot be guaranteed by this markdown file alone.

## Deterministic outcomes

- **PASS:** identity and grants exact; synthetic-only fixture; backup/restore checksums verified; all hashes match; every required result set complete; no unapproved schema/history/data change; all candidate-specific gates and post-run comparisons match; reviewer and approver sign the evidence.
- **FAIL:** a planned check completes and its expected value differs, such as a hash mismatch, schema mismatch, dependency conflict, altered aggregate, or unexpected grant. Preserve evidence and do not proceed.
- **STOP:** an identity, target, credential, isolation, output-completeness or authorization condition is uncertain or unexpected. Stop before the next phase and request review.
- **RESTORE:** any mutation outside the approved disposable scope, data loss, failed recovery check, or irreconcilable drift. Restore the verified baseline, recapture metadata/checksums, and obtain recovery sign-off. Never restore to staging or production.

## Recovery and disposal

Stop immediately on any unexpected write, data loss, constraint change, cross-database access, or account/grant mismatch. Restore the disposable database from the verified baseline, recapture metadata, compare checksums and aggregates, and obtain reviewer sign-off that recovery is complete. Do not attempt recovery against staging or production.

After review, destroy the throwaway database and temporary credentials through the authorized administrator, record the destruction evidence, and retain only sanitized logs and metadata. A successful rehearsal does not authorize staging execution, migration-history insertion, financial remediation, or deployment.

The commission-detail source defect is fixed in commit `8d4949655ee10bf58222befd5d2c20e0d79af12a`, but live rollback remains prohibited until a separately approved environment proves the exact dependency and recovery behavior. The 35 CREATE migrations must not be replayed against existing tables, and no history reconciliation may call a destructive `down()` path.

## Required deliverables before any future approval

The package must contain the identity/grants capture, baseline and post-run metadata, backup and restore checksums, exact migration hashes, command transcript without passwords or business rows, schema/history diffs, recovery evidence, reviewer and approver, and an explicit disposition for every affected migration. Missing evidence leaves the operation blocked.

## Controls requiring external enforcement

This proposal cannot itself enforce DNS/firewall isolation, account grants, filesystem/worktree separation, secret lifetime, process environment scrubbing, backup confidentiality, or destruction of the disposable host. An authorized administrator must provide evidence for each control. If any cannot be independently verified, provisioning approval is `STOP`.
