- Root-cause investigation discovered original `account_types` primary key IDs **0 and 1**, and source phpMyAdmin dump's header explicitly includes `SET SQL_MODE = "NO_AUTO_VALUE_ON_ZERO"`. The V2 importer was running only data-only INSERT statements, and previously did not restore the source's `NO_AUTO_VALUE_ON_ZERO` session setting. In default MySQL 8 mode, an explicit AUTO_INCREMENT zero can become an autogenerated ID 1, then collide with the explicit historical ID 1; this is the **strongest verified candidate** for the failure, not an observed SQLSTATE proof.

## Exact code fixes

1. `tools/database_v2/import_staged_mysql.php` now adds `NO_AUTO_VALUE_ON_ZERO` **only to the isolated import connection's SESSION sql_mode** for the transaction, while preserving the owner's explicit zero-timestamp policy by removing only `NO_ZERO_DATE`/`NO_ZERO_IN_DATE` when requested. Previous session mode is restored in `finally`; never changes GLOBAL/PERSIST server settings or deployed connections.
2. The importer **asserts original `account_types.id=0` and `id=1` both exist before committing** the real-data transaction. Failure rolls back all imported source entities; no invented key remapping.
3. Each individual INSERT now catches `QueryException`, rolls back, and exposes ONLY safe structured diagnosis: `table=<allowed_table>`, `statement=<ordinal>`, `sqlstate=<five-character code>`, `mysql_errno=<integer>`. It never logs the SQL statement, PDO bindings, per-user amounts, narrative, personal data, or raw MySQL message. This permits diagnosing any further strict MySQL compatibility errors with minimal sensitive exposure.
4. A data-only **synthetic** CI fixture now uses account type PKs zero and one in one historical INSERT and asserts both survive the actual disposable MySQL 8.4 import, with aggregate PK bounds. Windows CRLF source-staging SHA integrity and valid/invalid import rollback tests remain in CI.
